# verify

완료는 말이 아니라 증거로 판정한다.

## 1. 원칙

- 서브에이전트의 '완료' 보고만으로 완료 처리하지 않는다.
- 시험 결과는 메인이 로그의 통과·실패 줄을 직접 보고 확인한다. 요약 숫자만 믿지 않는다.
- 기준을 낮춰 통과시키지 않는다. 기준을 바꿔야 하면 사용자에게 이유와 함께 묻는다.
- 실행하지 못한 확인은 통과로 적지 않는다. 미검증으로 적는다.
- 독립 검토가 명시된 조건은 별도 주체 없이 충족했다고 판정하지 않는다. qa·reviewer·gate 관점을 직접 수행할 수 있지만 자기 검토는 독립 검토가 아니다.

## 2. 역할

| 확인 | 역할 |
| --- | --- |
| 시험·린트·타입 검사·빌드 실행과 증거 수집 | qa |
| 변경이 요청·규약에 맞는지 검토 | reviewer |
| 독립 검토가 필요한 완료 주장의 감사와 판정 | gate |

판정은 메인이 한다. 역할들은 증거를 모으고 의견을 낸다.

## 3. 절차

1. 완료 기준을 목록으로 펼친다. 계획과 `spec-first` 스킬의 수용 기준에서 가져오고, 기준 묶음의 필수 요소(기준 문서·이전 결정이 요구하는 것)도 기준으로 넣는다.
2. 기준마다 어떤 증거가 있으면 충족인지 정한다. 명령 출력, 시험 이름, 스크린샷, 파일 경로 등.
3. 구현 담당자가 실행한 관련 명령의 로그를 받는다. 빠진 검증만 직접 또는 qa로 보강한다.
4. 로그에서 통과·실패 줄을 직접 확인한다. 건수가 보고와 맞는지 본다.
5. 한 번의 통합 검토로 요구 정합·품질을 대조한다. 필요할 때만 reviewer에게 맡긴다. 지적이 있으면 고친 뒤 그 지적과 영향 범위만 다시 확인한다.
6. gate는 독립 검토가 명시된 조건이거나 사용자가 요구했을 때만 서브에이전트로 띄운다. gate에게 완료 주장, 기준 묶음, 증거 위치를 넘기고 반환된 판정을 보고에 쓴다. 생략했다면 보고에 생략했다고 쓴다.
7. gate 감사를 받았다면 감사 뒤 증거가 생겼을 때 그 묶음으로 다시 감사받는다. gate가 수정 필요나 미검증으로 판정하면 완료라고 보고하지 않는다.
8. gate·reviewer 판정이나 시험 뒤에 커밋이 생겼는지 본다. 생겼다면 그 판정·시험은 지금 코드를 지지하지 않는다. 다시 확인하거나 지난 판정이라고 보고에 쓴다.

## 4. 보고 형식

| 구분 | 내용 |
| --- | --- |
| 완료 | 기준과 증거(명령, 결과 줄, 경로) |
| 미완료 | 기준과 남은 일 |
| 미검증 | 확인하지 못한 기준과 이유, 확인할 방법 |

결과를 먼저 쓴다. 배경은 그다음이다.

## 점검 목록

- [ ] 완료 기준마다 증거가 있다. 기준 문서의 필수 요소도 기준에 넣었다.
- [ ] 시험 로그의 통과·실패 줄을 직접 봤다.
- [ ] 판정·시험 뒤에 생긴 커밋이 없는지 봤다.
- [ ] 기준을 낮추지 않았다.
- [ ] 통합 검토를 수행했다. gate는 필요한 경우(독립 검토 조건·사용자 요구)에만 거쳤다.
- [ ] 완료·미완료·미검증을 나눠 보고했다.

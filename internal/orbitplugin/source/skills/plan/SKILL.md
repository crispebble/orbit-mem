# plan

일을 받으면 먼저 성격을 판정한다. 판정에 따라 계획의 무게를 정한다.

## 1. 성격 판정

| 일의 성격 | 처리 |
| --- | --- |
| 단순하고 분명한 일 | 바로 처리한다. 별도 계획을 만들지 않는다. |
| 기존 규칙이 있는 일 | 관련 기록·결정의 원문을 확인한 뒤 처리한다. |
| 모호하거나 낯선 일 | 조사부터 한다. scoper와 `explore-domain` 스킬을 쓴다. |
| 되돌리기 어렵거나 비용·권한이 걸린 일 | 영향을 먼저 정리하고, 그 행동 직전에 채팅으로 승인받는다. |

파일 수만으로 절차를 늘리지 않는다. 단계가 여러 개여도 익숙하고 분명하면 바로 계획해 실행한다. 판정이 애매하면 가벼운 쪽에서 시작하고, 필요가 드러나면 그때 무거운 쪽으로 올린다. 단순한 일에 계획이나 다중 에이전트를 강제하지 않는다.

## 2. 큰 일의 계획 순서

1. **기준 찾기.** `spec-first` 스킬로 기준 명세·이전 결정·기존 조사를 원문으로 찾아 기준 묶음을 만든다. 메인이 직접 하며, 이후 모든 위임에 이 묶음을 넘긴다. 이 일이 개발 순서·로드맵의 한 항목이면 그 항목이 가리키는 기획·설계 원문까지 따라간다.
2. **읽기 전용 탐색.** 필요한 위치·흐름을 직접 확인하고, 독립 하위 질문의 분업 이득이 분명할 때 explorer·mapper에게 맡긴다. 이 단계에서 파일을 바꾸지 않는다.
3. **계획 전 인터뷰.** 사람 판단은 여기서 한 번에 모으고, 승인 뒤 실행은 단계마다 묻지 않는다. 단, 되돌리기 어려운 행동은 계획 승인과 별개로 실행 직전에 채팅 승인을 받는다.
   - **의도 판정을 한 줄로 알린다.** "의도가 분명합니다(원하는 결과: …)" 또는 "의도가 흐립니다(…가 정해지지 않았습니다)". 애매하면 분명으로 본다.
   - **질문 후보를 거른다.** 코드·문서·기준 묶음으로 답할 수 있으면 조사하고 묻지 않는다. 합리적 기본값으로 풀리면 기본값을 적고 묻지 않는다. 기준 묶음에 이미 정해진 결정, 사용자가 이번 요청에서 정했거나 "추천대로"로 승인한 범위는 다시 묻지 않는다.
   - **주인 결정은 기본값이 있어도 묻는다.** 되돌리기 어렵거나 데이터·보안에 닿는 것, 그리고 공개 범위·배포·외부 의존·데이터 구조·비용·규모·대상 사용자·제품 방향처럼 사용자가 계속 안고 갈 선택이다.
   - **결과를 실질적으로 바꾸는 미정 결정만 질문한다.** 의도가 분명하고 이미 승인된 범위면 인터뷰를 추가하지 않는다. 필요한 경우 한 번에 질문 1~3개, 질문마다 선택지 2~4개를 호스트 질문 도구가 있으면 그것으로 묻는다. 추천을 첫 선택지로 두고 근거를 한 줄 붙인다. 사용자가 건너뛰거나 "알아서"라고 하면 추천을 적용하고 적용했다고 밝힌다. 판정이 애매했으면 결과를 가장 크게 바꾸는 질문 하나만 하고, 사용자가 "다 물어봐"라고 하면 모든 갈림길을 묻는다.
   - **의도가 흐리면 먼저 조사한다.** 합리적 기본값을 정할 수 있으면 "이렇게 가정했습니다"를 눈에 띄게 알린다. 사람이 조정하지 않은 만큼 4·6번 점검을 엄격히 한다.
   - **매 질문 차례 끝에 결정 점검표를 확인한다.** 미정인 주인 결정이 남았을 때만 다음 질문을 한다. 기본값 항목은 계획 머리에 "가정"으로 적는다.

     | 항목 | 상태 |
     | --- | --- |
     | 원하는 결과(무엇이 되면 끝인가) | 정함 / 기본값 / 미정 |
     | 범위(포함·제외) | 정함 / 기본값 / 미정 |
     | 보존 조건(데이터·형식·화면·동작) | 정함 / 기본값 / 미정 |
     | 완료 기준(확인 방법) | 정함 / 기본값 / 미정 |
     | 주인 결정 각각 | 정함 / 미정 |
4. **빈틈 점검.** 빠진 전제·모순·기존 결정 충돌·범위 밖 요구를 직접 확인한다. 필요하면 scoper에게 기준 묶음을 넘겨 의도 판정과 질문 후보를 받고 3번에서 거른다(scoper는 사용자와 대화하지 않는다).
5. **계획 작성.** 직접 계획하거나 분업이 유익하면 planner에게 기준 묶음을 넘긴다. 단계·의존 관계·완료 기준을 쓰고 계획 머리에 기준 문서를 밝힌다.
6. **계획 검증.** 직접 검토하거나 독립 검토가 필요하면 plan-reviewer에게 계획과 기준 묶음을 넘긴다. 검토는 착수 가능 여부와 막는 요인(기준의 필수 요소 누락 포함)만 판정한다. 수정은 최대 두 번이다. 두 번 고쳐도 막히면 막는 요인을 사용자에게 보고한다.
7. **승인.** 새 제품 방향·범위 확대·미승인인 되돌리기 어려운 결정이 들어 있으면 계획 요약을 한 번 보여 주고 승인받는다. 그 외에는 바로 실행에 들어간다. 승인 뒤에는 끝까지 진행한다(되돌리기 어려운 행동의 실행 직전 채팅 승인은 계획 승인과 별개다). 사용자 답이나 외부 조치가 필요하면 그 이유를 밝히고 멈춘다.

## 3. 좋은 계획의 조건

- 단계 하나가 위임 한 번 크기다.
- 단계마다 확인 가능한 완료 기준이 있다.
- 계획 머리에 기준 문서 링크가 있고, 기준의 필수 요소마다 그것을 만드는 단계가 있다.
- 단계 사이 의존 관계가 드러나 있다. 동시에 해도 되는 단계를 표시한다.
- 동작을 바꾸는 단계는 `spec-first` 스킬의 수용 기준과 연결된다.
- 되돌리기 어려운 단계는 따로 표시하고, 그 단계 실행 직전에 채팅으로 승인받는다고 적는다.

## 4. 계획 보관

큰 계획서는 프로젝트가 명세·결정 문서를 두는 곳(연결된 문서 도구가 있으면 그곳)에 둔다.

계획서와 진행 기록에 같은 내용을 두 번 쓰지 않는다. 진행 기록에는 계획서 링크만 남긴다.

## 점검 목록

- [ ] 일의 성격을 판정했다.
- [ ] 기준 명세·결정·기존 조사를 원문으로 찾아 모든 위임에 넘겼다.
- [ ] 단순한 일에 계획을 강제하지 않았다.
- [ ] 질문은 결과를 바꾸는 결정으로 한정했고, 근거와 추천을 붙였다.
- [ ] 가정한 기본값을 밝혔다.
- [ ] 계획의 착수 가능성을 확인했다.
- [ ] 승인이 필요한 결정을 사용자에게 확인했다.

# Git Commit Rules (기본값)

이 문서는 레포에 자체 commit convention이 없을 때 적용하는 기본 규칙이다. 레포에 규칙이 있으면 그것을 우선한다.

PR 관련 규칙은 `pull-request` 스킬에 있다.

## 메시지 형식

- 기본 규칙은 Udacity Style이며 커밋 메시지는 다음 구조를 따른다.

```text
<type>: <subject>

<body>

<footer>
```

- `type`은 변경 종류를 나타내며 다음 값 중에서 선택한다.

| Type | 설명 |
| --- | --- |
| `feat` | 새로운 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 변경 |
| `style` | 코드 스타일 변경. 포맷, 세미콜론 등 로직 변경 없음 |
| `refactor` | 코드 리팩토링 |
| `perf` | 성능 개선. 쿼리 최적화, 캐시 도입 등 |
| `test` | 테스트 코드 |
| `chore` | 빌드, 설정, 의존성 등 기타 작업 |
| `revert` | 이전 커밋 되돌리기 |

- `pull-request` 스킬의 type 표에는 `hotfix`가 추가로 있다. 이는 배포 성격을 나타내는 PR 전용 값이며 커밋 type으로는 쓰지 않는다. 긴급 패치라도 커밋 type은 실제 변경 내용을 따라 `fix` 등을 쓴다.
- `subject`는 변경 요약이며 50자 이내를 권장한다. 영어 명령형 동사로 시작하고, 첫 글자는 대문자로 작성하며, 마침표를 사용하지 않는다.
- `body`는 선택 사항이며 무엇을 왜 변경했는지 설명한다. 한글로 작성하고 한 줄은 72자 이내로 줄바꿈한다. 어떻게 바꿨는지는 diff가 보여주므로 반복하지 않는다.
- `footer`는 선택 사항이며 이슈 번호 같은 메타 정보를 작성한다. 예: `Closes #123`.
- 좋은 예시는 `feat: Add todo creation API`, `fix: Handle todo completion state bug`, `refactor: Extract Github login service`이다.
- 나쁜 예시는 여러 레이어와 기능을 한 번에 묶는 `feat: Implement todo system` 같은 커밋이다.

## 트레일러

- 프로젝트가 참조 트레일러를 요구하면(예: `Ref: PROJ-####`) **커밋을 만들기 전에 그 번호를 먼저 확보한다.** 번호가 없다는 이유로 트레일러를 비운 채 커밋하지 않는다.
- 참조 대상이 아직 없으면 그것을 먼저 만들고 커밋한다. 그 생성 작업이 별도 커밋이면 순서를 그렇게 잡는다.
- 도구나 에이전트가 요구하는 공동 작성자 트레일러(`Co-Authored-By:`)는 해당 도구의 지침을 따른다.
- 트레일러는 body와 빈 줄로 분리하고 `Key: value` 형식으로 한 줄씩 작성한다.

## 커밋 단위와 시점

- 커밋은 하나의 관심사로 작게 유지한다. 여러 관심사를 하나의 큰 커밋으로 합치지 않는다.
- **전체 요청이 끝날 때까지 커밋을 미루지 않는다.** 독립적으로 설명하고 검증할 수 있는 작업 단위가 완료될 때마다 관련 변경만 선별해 커밋한다.
- 장기 작업에서는 직전 커밋 해시를 다음 작업의 기준점으로 사용한다.
- 기능 변경과 그 변경이 직접 영향을 준 테스트, 문서, 마이그레이션, API 계약은 같은 관심사로 취급해 함께 커밋한다. 문서가 실제 동작과 어긋난 상태로 코드만 커밋하지 않는다.
- 관심사가 다른 문서 정합성 수정은 `docs` 커밋으로 분리한다.
- 자동 생성 파일과 잠금 파일은 실제 생성 명령으로 변경된 경우에만 함께 커밋한다. 손으로 고쳐 넣지 않는다.

## 커밋 전 확인

- 커밋 전에 `git status`와 staged diff를 확인한다. 무엇이 들어가는지 보지 않고 커밋하지 않는다.
- **`git add -A`, `git add .`, `git commit -a`처럼 범위를 특정하지 않는 스테이징을 쓰지 않는다.** 커밋할 경로를 명시한다.
- 현재 작업과 무관한 변경, 사용자나 다른 도구가 만든 파일, 빌드 산출물, 로컬 실험 파일을 포함하지 않는다.
- 비밀값(API 키, 토큰, 비밀번호, 인증서, 개인키)과 개인정보가 diff에 없는지 확인한다.
- 기계별 로컬 설정 파일은 커밋하지 않고 `.gitignore`로 제외한다.
- pre-commit 훅이 커밋을 막으면 원인을 고친다. `--no-verify`로 우회하지 않는다.

## 에이전트 커밋과 사람 확인

- 에이전트는 작업 단위가 완료되면 커밋한다. 다만 **무엇이 들어갔는지 사람에게 보고한다** — 커밋 해시, 제목, 포함한 경로, 의도적으로 제외한 것.
- **푸시는 사람의 명시적 요청 없이 하지 않는다.** 커밋은 로컬이라 되돌리기 쉽지만 푸시는 바깥으로 나가는 행위다. 이 구분이 게이트의 기준이다.
- 원격 브랜치 생성, PR 생성·머지, 태그 푸시, 릴리스 발행, 이슈 코멘트도 같은 기준으로 사람의 요청을 받는다.
- 사람이 커밋 전 검토를 원한다고 밝히면 스테이징과 메시지 작성까지만 하고 staged diff를 보여준 뒤 멈춘다. 그 지시는 해당 작업이 끝날 때까지 유지된다.
- 커밋한 모든 줄의 책임은 사람에게 있다. 보고를 생략하면 사람이 검토할 기회 자체가 사라지므로, 보고는 커밋의 일부지 선택 사항이 아니다.

## 브랜치와 히스토리

- 기본 브랜치(`main`, `master`, `develop`)에 직접 커밋하지 않는다. 커밋 전에 `type/short-kebab-case-summary` 형식의 작업 브랜치를 만든다. 브랜치 규칙은 `pull-request` 스킬을 따른다.
- 다른 작업이 진행 중인 브랜치에 무관한 커밋을 얹지 않는다. 그 브랜치의 관심사와 섞여 머지할 때 함께 딸려간다.
- 아직 푸시하지 않은 자기 커밋은 amend와 rebase로 정리해도 된다.
- **이미 푸시한 커밋의 히스토리는 사용자 요청 없이 재작성하지 않는다.** amend, rebase, `push --force`, `push --force-with-lease`가 모두 해당한다.
- 되돌릴 때는 히스토리를 지우지 않고 `git revert`로 되돌리는 커밋을 남긴다. body에 되돌린 커밋 해시와 이유를 적는다.
- 대량 파일 삭제, 서브모듈 변경, 히스토리에 포함된 비밀값 제거는 실행 전에 사용자에게 확인한다.
